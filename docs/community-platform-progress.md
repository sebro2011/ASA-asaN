# Community platform: foundation work in progress

**Not production ready. Do not apply this migration or enable a community release yet.** This is a local foundation, not the six-phase platform. No live database changes or deployments were made as part of this work.

## Audit

The website is a Vite/React/TypeScript SPA backed by Express and Vercel functions, not Next.js. Its shared workspace auth uses a lazy Supabase client configured with a publishable key through the server. Its `profiles`, `conversations`, and `messages` tables are private workspace data and must not be reused for public profiles or social messaging. CosmoVision has its own video submission system and remains separate. The connected Supabase project currently has existing workspace tables; connected Vercel metadata identifies the existing website as Vite and exposes names, not values, of its Supabase configuration variables. Identifying the project as the one actually configured in Vercel requires verifying configuration securely; the sensitive URL value was not read.

## Implemented locally

`supabase/migrations/20261123000000_community_foundation.sql` introduces separate tables for pre-moderated text posts, comments, public display names and science groups, private group memberships, likes, private reports, private moderation notifications, suspensions and moderator membership. It has RLS, column privileges, database-enforced per-user insert and selected update limits and moderator-only SQL functions. Editing approved posts returns them to moderation. Moderator membership cannot be self-assigned through the public API. Moderator decisions record a minimal private audit entry and compare the reviewed text to prevent approval of a stale edit. The SQL test uses PGlite with simulated Supabase roles and identities, not a live Supabase instance. The migrations have not been applied to any project.

`supabase/migrations/20261123000001_community_direct_messages.sql` is a separate, locally tested draft for opt-in one-to-one text requests, participant-only messages, bilateral blocking, and private message reports with moderator-only review. Blocked participants cannot read or send, but can report previously received messages by ID. It reuses the database-enforced quotas and has no frontend. It is not ready for deployment or exposure: independent security review, abuse and race testing, a moderator UI and retention policy are required.

A new `/explore/community` destination reuses the shared account session and performs real Supabase queries for text posts, comments, likes, public display names, reports, moderator review queues and a private moderation notification inbox. It is translated in English, Sinhala and Tamil, provides loading/error states, and uses the existing responsive shell. Groups, posts, comments and display names require moderation. Group creation provisions the owner membership; members may join or leave approved public groups and submit group posts. Owners can promote, demote or remove members, and delegated admins can remove ordinary members. Rosters are available only to the owner and admins (first 100 members). Role changes are audited. The post filter only searches the currently loaded posts. It will show an unavailable state until the reviewed migration is applied. The UI has not been tested against hosted Supabase or on physical devices. A headless Chromium viewport test was attempted locally but the browser could not start because required NSS/NSPR shared libraries are missing.

## Release blockers and outstanding phases

- Community profiles currently contain only a moderated display name; full profile pages and profile search are not implemented. The text feed cannot operate against the current live schema.
- Moderators can retrieve, dismiss and remove reported post versions. Resolution of changed content marks the report stale instead of removing a newer version. The queue is minimal; there is no report escalation or audit-log interface. Deletion of a post cascades its reports, so durable evidence and retention policies need design before release. Moderation has no production operational procedure. Quotas need concurrency and abuse testing. The draft should receive independent security review before application.
- Media upload and validation, reactions beyond likes, threaded replies, hashtags, follows, server-side search and ranking are not implemented.
- Messaging has only a draft SQL foundation for opt-in one-to-one requests, consent, blocking and reporting; there is no messaging interface or deployed service. Group messages, realtime, read receipts, presence, media, notification delivery and comprehensive messaging privacy controls are not implemented. The notification inbox covers moderation decisions and report resolution only; it requires manual refresh and does not implement push or realtime updates. Do not enable direct messages until child-safety requirements and abuse response have been designed and independently verified. The report record currently cascades if the underlying message is deleted, so durable evidence and retention require explicit design.
- Groups have basic admin delegation, moderated creation and member-only posting, but no group editing, dedicated group moderation, threaded discussions, server-side search or trending. Comprehensive moderation workflows and the rest of the translated responsive UI are not implemented.
- A read-only catalog check of the accessible Supabase project found RLS enabled on its nine existing public tables; this is not an authorization test and does not verify the project is the one configured in Vercel. The community schema has not been applied. Hosted community RLS, Realtime, Storage, integration, accessibility and cross-device tests remain outstanding. The PGlite test cannot establish compatibility with hosted Supabase configuration or replace adversarial security testing.

## Eventual deployment procedure

First finish and review all missing features and threat models, particularly safeguards for younger users. Verify the actual configured project securely, back it up, test migrations and RLS in an isolated environment using representative roles, and establish operational moderator and incident-response procedures. Only after explicit deployment approval should an authorized operator apply reviewed migrations and deploy the application. Do not store service-role credentials in browser code or source control.
