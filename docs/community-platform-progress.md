# Community platform: foundation work in progress

**Not production ready.** The community foundation was applied to the connected production database with user approval to restore the unavailable feed. The separate direct-message migration remains an unreviewed draft and must not be applied. This is not the complete six-phase platform.

## Audit

The website is a Vite/React/TypeScript SPA backed by Express and Vercel functions, not Next.js. Its shared workspace auth uses a lazy Supabase client configured with a publishable key through the server. Its `profiles`, `conversations`, and `messages` tables are private workspace data and must not be reused for public profiles or social messaging. CosmoVision has its own video submission system and remains separate. The live website’s public workspace configuration identifies the connected Supabase project; the project’s Auth, database and REST services reported healthy during the restoration check.

## Implemented locally

`supabase/migrations/20261123000000_community_foundation.sql` introduces separate tables for pre-moderated text posts, comments, public display names and science groups, private group memberships, likes, private reports, private moderation notifications, suspensions and moderator membership. It has RLS, column privileges, database-enforced per-user insert and selected update limits and moderator-only SQL functions. Editing approved posts returns them to moderation. Moderator membership cannot be self-assigned through the public API. Moderator decisions record a minimal private audit entry and compare the reviewed text to prevent approval of a stale edit. The SQL test uses PGlite with simulated Supabase roles and identities, not a live Supabase instance. The foundation was applied to the connected production project as migration `20261123162752` (`community_foundation`). The SQL was submitted through the Supabase management API with equivalent statements and whitespace formatting. The direct-message migration was not applied.

`supabase/migrations/20261123000001_community_direct_messages.sql` is a separate, locally tested draft for opt-in one-to-one text requests, participant-only messages, bilateral blocking, and private message reports with moderator-only review. Blocked participants cannot read or send, but can report previously received messages by ID. It reuses the database-enforced quotas and has no frontend. It is not ready for deployment or exposure: independent security review, abuse and race testing, a moderator UI and retention policy are required.

A new `/explore/community` destination reuses the shared account session and performs real Supabase queries for text posts, comments, likes, public display names, reports, moderator review queues and a private moderation notification inbox. It is translated in English, Sinhala and Tamil, provides loading/error states, and uses the existing responsive shell. Groups, posts, comments and display names require moderation. Group creation provisions the owner membership; members may join or leave approved public groups and submit group posts. Owners can promote, demote or remove members, and delegated admins can remove ordinary members. Rosters are available only to the owner and admins (first 100 members). Role changes are audited. The post filter only searches the currently loaded posts. Anonymous REST reads of posts, profiles and groups succeeded after the foundation was applied; full browser and authenticated interaction testing remains outstanding. No moderator is provisioned yet, so submitted content remains pending until an authorized operator assigns a moderator. The UI has not been tested against hosted Supabase or on physical devices. A headless Chromium viewport test was attempted locally but the browser could not start because required NSS/NSPR shared libraries are missing.

## Follow-up verification

A read-only hosted catalog check found RLS enabled on all 12 community tables and no anonymous table-level INSERT privilege on them. The private audit, moderator, suspension and rate-limit tables have no client SELECT privilege; report SELECT is also denied to both client roles. This is a metadata check, not a test of row isolation. Moderator count remains zero. The hosted `community_can_write()` helper unexpectedly has anonymous EXECUTE privilege despite the migration revoking PUBLIC access; its SQL requires a non-null `auth.uid()` and returns only a boolean, but the extra grant should be reviewed and reconciled in an approved future migration. Other community security-definer functions checked have a fixed search path and anonymous EXECUTE denied.

The production community URL returned rendered anonymous page content with a sign-in prompt and an empty approved-post state. A captured `Loading groups…` state does not prove that the asynchronous group request completed. Supabase Auth, DB, REST and Storage health checks reported healthy. Realtime health returned unhealthy once and healthy on an immediate retry; the healthy response still reported `db_connected: false` and `replication_connected: false`, so realtime operation is not established. No live writes or changes were made. Local community tests passed 17/17 (including PGlite simulated-role SQL and jsdom UI tests), security-header tests 11/11, and security-performance tests 8/8. These do not replace hosted authenticated, adversarial, browser/device or concurrency tests.

## Release blockers and outstanding phases

- Community profiles currently contain only a moderated display name; full profile pages and profile search are not implemented. The basic text feed has its schema, but end-to-end authenticated behavior remains unverified.
- Moderators can retrieve, dismiss and remove reported post versions. Resolution of changed content marks the report stale instead of removing a newer version. The queue is minimal; there is no report escalation or audit-log interface. Deletion of a post cascades its reports, so durable evidence and retention policies need design before release. Moderation has no production operational procedure. Quotas need concurrency and abuse testing. The deployed foundation still needs independent security review and operational moderation.
- Media upload and validation, reactions beyond likes, threaded replies, hashtags, follows, server-side search and ranking are not implemented.
- Messaging has only a draft SQL foundation for opt-in one-to-one requests, consent, blocking and reporting; there is no messaging interface or deployed service. Group messages, realtime, read receipts, presence, media, notification delivery and comprehensive messaging privacy controls are not implemented. The notification inbox covers moderation decisions and report resolution only; it requires manual refresh and does not implement push or realtime updates. Do not enable direct messages until child-safety requirements and abuse response have been designed and independently verified. The report record currently cascades if the underlying message is deleted, so durable evidence and retention require explicit design.
- Groups have basic admin delegation, moderated creation and member-only posting, but no group editing, dedicated group moderation, threaded discussions, server-side search or trending. Comprehensive moderation workflows and the rest of the translated responsive UI are not implemented.
- A read-only catalog check found RLS enabled on all 12 community tables; anonymous REST reads of the public feed, profiles and groups returned successfully. These checks do not establish full authorization correctness. Hosted community RLS, Realtime, Storage, integration, accessibility and cross-device tests remain outstanding. The PGlite test cannot establish compatibility with hosted Supabase configuration or replace adversarial security testing.

## Eventual deployment procedure

The management API assigned version `20261123162752` to the applied foundation while the repository file is named `20261123000000_community_foundation.sql`. Reconcile migration history and ordering before using automated migration deployment: blindly replaying the foundation will fail because its objects already exist, and blindly pushing all pending files could apply the unfinished direct-message migration. Do not mark migrations applied without first verifying schema equivalence and migration history. Establish operational moderator and incident-response procedures and independently review the deployed foundation. Finish and review all missing features and threat models, particularly safeguards for younger users; back up and test future migrations and RLS in an isolated environment. Only after explicit deployment approval should an authorized operator apply further migrations and deploy the application. Do not store service-role credentials in browser code or source control.
