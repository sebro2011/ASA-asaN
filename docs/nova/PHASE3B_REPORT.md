## 2. Migrations

Three additive migrations. They are idempotent (`if not exists`, `create or replace`, `drop policy
if exists`) and were replayed twice in the test harness to prove it.

**Tables (9):** `profiles`, `projects`, `conversations`, `messages`, `message_revisions`,
`documents`, `document_revisions`, `knowledge_files`, `tasks`.

**Functions (6):**

| Function | Behaviour |
| --- | --- |
| `set_updated_at()` | trigger: keeps `updated_at` monotonic |
| `handle_new_user()` | creates the profile row on signup, from `auth.users` |
| `touch_conversation()` | maintains `seq` and `last_message_at` on insert |
| `prune_document_revisions()` | keeps the newest 20 revisions per document |
| `enforce_workspace_quota()` | 500 conversations / 1000 documents / 5000 tasks / 100 MB files; raises SQLSTATE `54000`, message contains `quota-exceeded` |
| `delete_my_workspace_data()` | `security definer` RPC that deletes the caller's rows, keeps the profile |

**Reuse, not duplication:** `supabase/cosmovision.sql` is untouched and unmodified; the new schema
mirrors its conventions (RLS-first, `auth.uid()` ownership) but uses distinct table names.

**Rollback:** `20261105_nova_workspace_rollback.sql` is manual and destructive by design — it drops
storage policies, then functions, then the trigger, then tables child-first. It never touches
`auth.users` and never deletes bucket bytes, so a rolled-back deployment can be re-migrated without
losing accounts.

## 3. RLS policies

**33 table policies** — `select`/`insert`/`update`/`delete` for all nine tables except the two
revision tables, which are select/insert only (append-only history):

- `profiles` — own row; the only table where `insert` is allowed through `handle_new_user` and a
  self-insert fallback.
- `projects`, `conversations`, `documents`, `tasks`, `knowledge_files` — `auth.uid() = user_id`,
  `with check` on write, so a forged `user_id` is refused.
- `messages`, `message_revisions`, `document_revisions` — ownership through the parent row
  (`exists (select 1 from conversations c where c.id = conversation_id and c.user_id = auth.uid())`),
  so a foreign `conversation_id` is rejected even if the caller owns nothing.
- `anon` has **no** grants on any table or function (`revoke all ... from anon`).
- No policy uses `using (true)`; the harness asserts this.

**Storage (4 policies)** — private `knowledge` bucket (25 MB limit, 7 MIME types). Every policy
checks `(storage.foldername(name))[1] = (select auth.uid())::text`, i.e. a user's files live under
`<uid>/…` and cannot be read, listed, overwritten or deleted by anyone else.

## 4. Authentication features

- **Email + password only.** No mock auth, no anonymous sessions, no OAuth provider that would need
  credentials nobody has supplied.
- **Email confirmation required.** `AuthPanel` handles the unconfirmed state with a *Check your
  inbox* screen and a resend action; the profile surface re-exposes resend.
- **Password reset** by email link; **change password** for a signed-in user.
- **Session handling:** PKCE, `persistSession`, `autoRefreshToken`, storage key `nova-auth`;
  `onAuthStateChange` is subscribed in its own effect and unsubscribed on unmount.
- **Guard, not redirect:** `RequireAuth` renders the sign-in panel in place, so a deep link keeps its
  URL and the user lands on the page they asked for.
- **Profile bootstrap:** display name, locale, theme, motion, contrast, sidebar state, font scale,
  preferred provider, default surface — all mirrored to the cloud, device value wins on first
  sign-in, cloud fills a fresh device.
- **Unconfigured deployments** explain themselves (`Cloud workspace is not configured` …) and offer
  no fake form; Explore keeps working.
- **Account surface:** display-name save, resend verification, local-history import/remove, JSON data
  export download, and a destructive delete that calls `delete_my_workspace_data()` behind an
  explicit confirmation. Account deletion itself is deferred (see §7).
- **Security posture:** only the publishable/anon key reaches the browser, fetched at runtime from
  `/api/workspace/config` with `no-store`; the service-role key is never read by the new code and a
  static test fails the build if it ever appears in `src/`.

## 5. Sync features

On-demand sync, as approved — no Realtime subscription, no polling loop.

- **Outbox** (`nova_sync_outbox_v1`): one entry per `(table, id)`, newest payload wins, a queued
  delete supersedes a queued upsert, cap 400 (oldest dropped), 5 attempts then dead-letter.
- **Trigger points:** after a sign-in, on window focus, on `online`, on tab visibility, and after
  writes. The chip in the top bar shows `Synced · n waiting · n failed` and can be clicked to sync.
- **Conflict rule:** every push carries the `updated_at` it was based on. If the cloud row is newer,
  the push is dropped, the entry is cleared and the conflict is surfaced — a stale device edit can
  never overwrite a newer one.
- **Idempotency:** replaying a drained queue is safe (upsert by primary key), proven by test.
- **Offline:** nothing is sent, nothing is lost; the queue survives a reload.
- **Legacy import** (`nasa_ai_chat_thread_v3`): read-only — the local key is never deleted. The
  marker is written *before* the first cloud write, the conversation id is reused on retry, and the
  server message count must match the parsed count or the import reports failure (max 100 messages).

- **No Realtime**, per your decision. Two tabs converge on the next focus/online/write, not instantly.
- **Cloud writes are wired into the data layer, not into every future module.** The repositories,
  outbox and engine are ready and tested; Conversations/Documents/Tasks (Phases 4) are the callers.
- Legacy import is capped at 100 messages by design, so a very long old thread is truncated rather
  than silently heavy.

**Required environment variables** (names only, no new ones invented):

```
SUPABASE_URL=""                     # https://<project-ref>.supabase.co — bare origin only
SUPABASE_PUBLISHABLE_KEY=""         # sb_publishable_… or the legacy anon key — public by design
SUPABASE_SERVICE_ROLE_KEY=""        # server-only; unused by Phase 3B code
```

The endpoint answers `{enabled:false, reason}` for `not-configured | invalid-url | invalid-key |
key-conflict`, so a misconfiguration degrades to the unconfigured UI instead of a broken sign-in.

## 8. Manual Supabase steps

1. **Create the project** (or reuse the CosmoVision one — the new tables do not collide).
2. **Authentication → Providers → Email:** enable it; set *Confirm email* to **on** (the UI expects
   confirmation); set the *Site URL* to your deployment origin and add `…/profile` to
   *Redirect URLs*.
3. **SQL editor:** run `supabase/migrations/20261105_nova_workspace.sql`, then
   `20261105_nova_workspace_storage.sql`. Both are idempotent.
4. **Storage:** confirm a **private** bucket named `knowledge` exists with a 25 MB limit.
5. **Project settings → API:** copy the URL and the **publishable/anon** key into the server env
   (`SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`). Never paste the service-role key into any variable
   the client can reach.
6. **Deploy the server** (the config route must be reachable) and open `/api/workspace/config`; it
   should return `{"enabled":true,"url":…,"publishableKey":…}` with `cache-control: no-store`.
7. **Smoke test:** sign up in a private window → confirm the email → sign in → the top bar shows the
   sync chip and the home page shows the signed-in cloud card. Sign in on a second device and confirm
   the profile/preferences arrive.
8. **Verify RLS by hand:** with the anon key, `select * from conversations` must return 0 rows, and
   `select * from profiles` must return only your own row.
9. **Rollback plan:** `20261105_nova_workspace_rollback.sql` (drops tables/functions/policies; keeps
   accounts and bucket bytes). Take a database backup first — the script is destructive.
